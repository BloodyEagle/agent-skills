## План A. Универсальный режим: фреймворк-часть не мешает неподдерживаемым CMS

Цель: `info` честно сообщает «CMS не определена», модель работает штатными PHP-средствами, битриксовые/ларевелевские подсказки и пустые профильные ops исчезают.

### Ф1. Единый детект режима (`fsx.js` или новый `lib/detect.js`, `index.js`)
- `detectMode(root)` → `bitrix` | `laravel` | `generic` (приоритет: маркеры Битрикса → Laravel → generic); `ctx.laravel` заменяется на `ctx.mode`; в `index.json` хранится режим, VERSION=3 → разовая пересборка.
- Проверка: на фикстурах bitrix/laravel режим определяется как сейчас, на MODX и пустой папке — `generic`.

### Ф2. Режимные skip/docroot/классификация (`fsx.js`, `index.js`, обёртка classify)
- Skip-правила по режиму: generic — только `vendor/` у корня + SKIP_DIRS; `storage/`, `bootstrap/cache/`, битриксовые пути — только в своих режимах (сейчас `storage/` режется везде).
- Docroot в generic-режиме не ищется (весь проект — корень); `classify()` битрикса применяется только в режиме `bitrix`, `laravelClassify` — только в `laravel`; в generic узлы помечаются нейтрально (`php`/`page`), битриксовые теги не прилипают (сейчас `lang/ru/...` в любой папке помечается как lang).
- Рёбра `e/m/x/t/l` (события/модули/компоненты/шаблоны/lang) строятся только в `bitrix`, ларевелевские — только в `laravel`; универсальные `c/f/i` — всегда.

### Ф3. Чистые отказы ops (`bx.js`)
- Один guard при диспетче: профильные ops (`component/events/lang/route/table` — Битрикс; `routes/model/container/blade/console` — Laravel) в чужом/generic-режиме отвечают одной строкой «CMS не определена — операция доступна в проектах <список>», exit 1, без hint'ов.
- Из `symbol`/`search`/`outline`/`component` убираются битриксовые приписки «core:true включит их» вне режима `bitrix` (сейчас они уводят модель индексировать лишнее — подтверждено на MODX-фикстуре).
- `info` в generic-режиме: «CMS/фреймворк не определена — универсальный режим», состав файлов, кодировки, топ по строкам, доступный набор ops. Метку «(D7)» в «стиле кода» показывать только в Битриксе.

### Ф4. SKILL.md + references
- Правила 6–8 (битриксовые сценарии) переезжают в `references/bitrix.md`, ларевелевское правило 7 — в `references/laravel.md`; SKILL.md оставляет универсальные правила + абзац «после info: Битрикс → читай bitrix.md, Laravel → laravel.md, иное → профильные ops не вызывать».
- Эффект: SKILL.md перестаёт расти с каждым фреймворком (сейчас 19 КБ) и перестаёт толкать модель в битриксовые сценарии на MODX — источник большинства «ошибок».

### Ф5. Самопроверка и регрессия
- selftest: detectMode на маркерах, сообщения-отказы, нейтральная классификация.
- Фикстура `gen-plain-fixture.js` (нейтральный composer-проект с `vendor/`): vendor вне индекса, ops-отказы чистые, граф `c/f/i` работает.
- Регрессия: прогон bitrix/laravel/MODX-фикстур до и после — вывод неизменен для поддерживаемых режимов.

Риск: регрессия основных сценариев — закрывается Ф5 и поэтапными коммитами (по фазе на коммит).

## План B. Поддержка MODX (поверх Плана A)

Цель: на MODX скилл распознаёт CMS, не индексирует мусор, понимает раскладку и файловые элементы; честно объявляет ограничение «элементы в БД невидимы».

### Ф1. Детект и skip (`lib/detect.js`, `fsx.js`)
- Маркеры Revolution: `core/` + `manager/` + `connectors/`; Evolution: `manager/` + `assets/` + `includes/`. Версия — из `core/composer.json` (3.x).
- Skip в режиме modx: `core/vendor/`, `core/cache/`, `core/packages/`, `setup/` — решает исходную жалобу на медленность (главный источник — vendor из тысяч файлов).

### Ф2. Разбор .tpl и MODX-тегов (`lib/modx.js`, ~150–200 строк; индекс получает ext `.tpl` в режиме modx)
- Парсер тегов: `[[!snippet? &p=]]`, `[[$chunk]]`, `[[++setting]]`, `[[+ph]]`, `{{chunk}}` (Evolution), Fenom `{include 'file:...'}` / `{extends file=...}`.
- Рёбра: чанк/шаблон → файловый чанк по `file:`-префиксу; вызов тега → файловый элемент, если он есть в файлах (`core/components/<ns>/elements/`, `assets/components/`); `runSnippet('x')` в PHP → файловый сниппет. Неразрешимые (DB) вызовы не роняют граф.
- `outline` для .tpl: вызванные сниппеты/чанки/плейсхолдеры — как сейчас делает для битриксовых шаблонов.

### Ф3. Ops режима modx (`bx.js`, по образцу laravel-ops)
- `element name=X` — где определён файловый элемент и кто его вызывает тегом.
- `tpl name=...` — карта шаблона: теги, сниппеты, чанки, Fenom-include, кто рендерит.
- `route` в режиме modx — честный отказ: URL→ресурс хранится в БД (в SKILL.md предупреждение).
- `info`: версия MODX, список extras (`core/components/*`), число .tpl, **явное предупреждение**: «сниппеты/плагины/чанки/шаблоны в БД не индексируются» + указание модели искать их использование штатным `search` по тегам.

### Ф4. SKILL.md/references/selftest/фикстура
- Короткая режимная секция в SKILL.md + `references/modx.md` (раскладка, ограничение БД, паттерн работы).
- selftest: классификация путей MODX, парсер тегов на встроенных примерах.
- Расширение `gen-modx-fixture.js`: extra с файловым сниппетом, static element, .tpl с тегами и Fenom — smoke-прогон symbol/element/tpl/search.

### Ф5. Опционально, отдельным решением: чтение элементов из БД
- read-only SELECT (`modSnippet`, `modPlugin`, `modChunk`, `modTemplate`, `modx_site_content` для route) по кредам из `core/config/config.inc.php`; нужен mysql-клиент или node-драйвер (зависимость — против философии zero-deps), креды не попадают в вывод, запись запрещена. Требует отдельного подтверждения — в план не включён.
