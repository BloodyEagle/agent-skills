# automateskill — отложенная задача из свободного описания

> **Скилл работает только в ZCode.** Он опирается на инструменты ZCode: `CronCreate` (персистентные автоматизации по расписанию), `ListModels`, субагентов из `.zcode/agents/` с моделями вида `провайдер/модель$уровень`. В других агентах (Claude Code, Kilo Code, Codex, Gemini CLI и т.п.) скилл загрузится, но шаги выполнить не сможет — там нет этих механизмов.

Превращает сообщение вида «в 03:00 запусти задачу: в репозитории X проанализируй код моделью Y, сохрани отчёт и напиши план исправления, затем моделью Z выполни этот план в ветке Q — каждый пункт отдельный коммит, отчёт сохрани, запушь в git» в два артефакта:

1. **План-файл** с frontmatter в runner-репозитории: `C:\p\automatization\tasks\input\<slug>\00-<краткое-имя>.md`.
2. **Выделенная автоматизация** (`CronCreate`) на указанное время, которая выполняет планы из своей папки зарегистрированными субагентами.

Планы выделенных автоматизаций лежат в подпапке `tasks/input/<slug>/`. Перед созданием проверь промпты других автоматизаций runner: отсутствие пересечений гарантируется только если они действительно сканируют корень `tasks/input` и игнорируют подпапки. Время 03:01 и состав таких автоматизаций скилл не задаёт.

## Шаг 1. Извлеки параметры из текста

| Параметр | Примеры формулировок | По умолчанию |
|---|---|---|
| Расписание | «в 03:00», «каждый день в 9», «через 2 часа», «по будням в 21:30» | спросить |
| Повторение | «запусти» (разово) / «ежедневно», «каждый день» | разово, если повторение не указано; спросить только при неоднозначности |
| Целевой репозиторий | «в репозитории X», URL, локальный путь | спросить |
| Путь локальной копии | «копия в C:\p\…» | клон в `C:\Users\KuninAA\.zcode\repos\<имя>` |
| Исполнитель фазы 1 (модель Y) | «проанализируй моделью Y» | спросить — модель не выбирается молча |
| Исполнитель фазы 2 (модель Z) | «выполни план моделью Z» | из описания; фаза 1 предписывает записать её во frontmatter сгенерированного плана; не названа — спросить |
| Фоллбек-модель | «если упадёт — переключайся на …», «без фоллбека» | спросить всегда, если пользователь её не назвал: какая модель для фоллбека или «без фоллбека» |
| Ветка | «в ветке Q» | `obs/<имя-плана>` |
| Суть работы | свободный текст | — |

Модели-исполнители берутся только из описания пользователя. Известные псевдонимы текущего пула (просто ускоряют разбор, не значения по умолчанию): `gpt-6-astra`/«астра» → `plan-executor`; `gpt-6.1-sol`/«сол» → `plan-executor-sol`. Любая другая модель — новый агент-исполнитель (шаг 2, п. 3). Отчёт по умолчанию пишется в `tasks/done` целевого репозитория — спрашивать, только если пользователь хочет иначе.

## Шаг 2. Проверь окружение

1. Runner существует: `C:\p\automatization`. Нет — спроси актуальный путь.
2. **Текущий workspace** содержит определения всех выбранных исполнителей и фоллбеков в `.zcode/agents/`? Автоматизация привяжется к текущему workspace и будет порождать только его агентов. Файлы `plan-executor.md` и `plan-executor-sol.md` нужны только если выбраны именно эти агенты. Если нужных файлов здесь нет — остановись и спроси: выполнить скилл в workspace с агентами (там, где они зарегистрированы) или скопировать определения агентов в текущий workspace. Прочитай выбранные определения: архивирование, отчёт, коммиты по пунктам и merge в `main` должны быть предписаны исполнителю; сам `CronCreate` этих действий не выполняет.
3. **Проверь доступность каждой названной модели** (основной и фоллбек) через `ListModels`: точное совпадение полного id или однозначный суффикс. Модель найдена и не помечена `disabled` — запомни её полный id и доступные уровни рассуждения. Модель не найдена, отключена, совпадение неоднозначно или модель не названа — **выведи пользователю полный список моделей** (таблица: провайдер, модель, уровни рассуждения, доступность) и попроси выбрать доступную; без выбора не продолжай. Уровень бери только из списка хоста, не придумывай. Для фоллбека дополнительный допустимый ответ — «без фоллбека».
4. Названная модель есть в `ListModels`, но вне пула агентов — предложи создать нового агента-исполнителя: копия `plan-executor.md` с `name: executor-<короткое-имя>` и `model: <полный id>$<уровень>` в `.zcode/agents/` текущего workspace (напомни: новый агент зарегистрируется для свежих сессий — автоматизация, созданная сейчас, заработает с ним; правки уже зарегистрированных агентов в живой сессии не подхватываются).

## Шаг 3. Доспроси недостающее

Собери недостающее через `AskUserQuestion` одним батчем (до 4 вопросов: расписание, репозиторий, фоллбек, ветка). Фоллбек, если не resolved на шаге 2, — вопрос «какая модель для фоллбека (список из шага 2) или без фоллбека?». Один-два коротких вопроса можно задать текстом. Не придумывай значения сам.

## Шаг 4. Проверь права на push; нет прав — запроси авторизацию; чужое — форк

Репозиторий известен после шагa 3. Проверь до создания плана — план, который ночью упадёт на push, остановится с STOPPED и потеряет запуск.

1. Проверка прав:
   - Для локальной копии проверь URL `origin` и основную ветку; `git -C <путь> push --dry-run origin main` — лишь диагностика: отказ может быть вызван non-fast-forward или защитой ветки, а ответ «Everything up-to-date» сам по себе не доказывает права на запись.
   - Для GitHub: `gh api repos/<owner>/<repo> --jq .permissions.push` → `true` / `false`. Ошибку авторизации, 404 или сетевой сбой не выдавай за подтверждённое отсутствие прав: сначала уточни URL, доступ к приватному репозиторию и состояние авторизации.
   - `gh` не установлен или не авторизован — сначала наладь CLI/авторизацию, затем повтори проверку. Проверка клоном (`git clone --depth 1` + `git push --dry-run`) — только диагностика, не замена авторизации.
2. Прав нет — **запроси авторизацию у пользователя** и дождись её:
   - GitHub: попроси пользователя выполнить в терминале `gh auth login` (интерактивный вход от имени агента выполнить нельзя). Для чистого git-ремоута — добавить учётные данные в Git Credential Manager (например, один раз сделать push вручную).
   - После подтверждения пользователя («готово») повтори проверку из п. 1.
3. Права появились → репозиторий считается своим: работаем с оригиналом, форк не нужен.
4. После авторизации подтверждено отсутствие прав на оригинал → предложи форк и дождись согласия, затем `gh repo fork <owner>/<repo> --clone=false`. Найди фактический URL форка через GitHub CLI, не выводи его только из логина и имени оригинала. Форк может отставать от апстрима — синхронизируй при необходимости: `gh repo sync <owner-форка>/<repo-форка> --branch main`. Пользователю скажи явно: «пуш будет в твой форк <URL>; в апстрим изменения не попадут — PR с форка вручную». Если пользователь против форка или права остались неизвестны — останови скилл, план не создавай.
5. В frontmatter плана итоговый репозиторий (оригинал или форк) подставь в `repo:` (или `repo-path:` на его локальную копию) — вся механика (ветки, merge в main, архив, push) дальше работает без изменений.

## Шаг 5. Создай план-файл

Прочитай `references/plan-template.md` и следуй ему: frontmatter (`repo`/`repo-path`, `worktree`, `executor`, `branch`) + тело задачи по пунктам. Многофазную задачу («анализ → план исправлений → выполнение») оформи по разделу «Цепочка фаз» шаблона: тело фазы 1 предписывает исполнителю составить следующий план в эту же папку с `executor:` модели Z.

Файл плана: `C:\p\automatization\tasks\input\<slug>\00-<краткое-имя>.md`. Слаг папки — латиница, цифры, дефис (например `code-audit-myrepo`).

## Шаг 6. Закоммить план в runner

```bash
git -C C:/p/automatization add -- tasks/input/<slug>/00-<краткое-имя>.md
git -C C:/p/automatization commit -m "input: план <slug> (<краткая суть>)"
git -C C:/p/automatization push origin main
```

Перед коммитом проверь staged diff: он должен содержать только этот план. Если публикация плана на GitHub не была явно разрешена запросом пользователя, сначала получи согласие. Push упал — остановись и сообщи: без успешного push автоматизация не сможет забрать план.

## Шаг 7. Создай автоматизацию

Прочитай `references/automation-prompt.md`, подставь `<REPO_PATH>`, `<RUNNER_URL>`, `<PLANDIR>`, `<EXECUTORS>`, `<FALLBACKS>`, `<MODELS>` и `<TITLE>` и передай итоговый промпт в `CronCreate`. `<RUNNER_URL>` — проверенный remote runner, не обязательно URL из примера. `<EXECUTORS>` — все исполнители обеих фаз и выбранные фоллбеки; `<FALLBACKS>` — явное соответствие каждого исполнителя его фоллбеку либо «нет». Второй исполнитель цепочки фаз сам по себе не является фоллбеком:

- Любая задержка от текущего момента («через N минут», «через 2 часа») — `delayMinutes` в целых минутах, без `cron`, с `recurring: false`; текущий момент определяет хост.
- Абсолютное время или календарное расписание — `cron` в **локальной зоне** машины (проверь `tzutil //g`; «ежедневно в 03:00» при зоне MSK → `0 3 * * *`). Разовый запуск — `recurring: false`, повторяющийся — `recurring: true`.
- «Каждые N минут/часов/дней/недель/месяцев/лет» — обязательная пара `intervalUnit` и `interval` (1–200) плюс допустимый пятичастный `cron` для времени суток/календарных слотов. Например, каждые 40 дней в 09:00: `intervalUnit: daily`, `interval: 40`, `cron: "0 9 * * *"`. Не записывай длинный интервал недопустимым cron-шагом.
- Ровно N запусков — `recurring: false`, `maxRuns: N`; для единственного запуска `maxRuns` не нужен. С `recurring: true` `maxRuns` не передаётся.
- `title` — сохрани формулировку времени пользователя: «<его фраза про время>: <slug>». Параметров workspace и модели у `CronCreate` нет: workspace привязывает хост, пути runner и планов указываются в промпте.

## Шаг 8. Проверь и отчитайся

`CronList`: статус `active`, корректный `nextRunAt`. В ответе пользователю: id автоматизации, время следующего запуска, путь план-файла, список исполнителей, куда упадут отчёты. Предупреждения (коротко, всегда):

- Модель самой автоматизации — дефолтная хоста; ошибка «Automation 模型选择不可用…» чинится только в UI (Automations → настройки задачи → выбрать модель и уровень).
- `reasoning-level-missing` у субагентов означает, что в `model:` агента нет `$уровень`.
- Не удалять workspace, к которому привязана автоматизация.

## Ограничения

- Исполнитель — только из файлов `.zcode/agents/` текущего workspace; «модель X» вне пула требует создания агента (шаг 2).
- Права на push проверяются скиллом до создания плана (шаг 4); при отсутствии прав запрашивается авторизация пользователя, затем — форк. Ошибка push во время ночного выполнения всё равно возможна (права отозваны, сеть) — план остановится (STOPPED) с отчётом.
- Работа с форком не попадает в апстрим: изменения живут в вашем форке; PR в оригинал — вручную.
- Лимит механизма — 10 планов за запуск; цепочка фаз не должна зацикливаться (план порождает план порождает план…).
