# Шаблон план-файла (tasks/scheduled/<slug>/NN-имя.md)

Файл исполняется субагентом plan-executor / plan-executor-sol (их определения — в `.zcode/agents/` workspace автоматизации). Тело — на русском, UTF-8, пункты по порядку.

## Структура

```markdown
---
repo: https://github.com/<owner>/<repo>.git   # целевой репозиторий (URL)
# ЛИБО repo-path: C:\p\<repo>                 # существующая локальная копия вместо repo
# worktree: C:\repos\<repo>                   # необязательно: свой путь клона для repo
executor: plan-executor                       # или plan-executor-sol, или другой агент пула
# branch: obs/custom-name                     # необязательно, по умолчанию obs/<имя-плана>
---

1. <Первый пункт — конкретное действие>.
2. <Второй пункт>.
...
```

Правила для frontmatter:
- `repo:` должен указывать на репозиторий с правами на push у этого компьютера. Если исходный репозиторий чужой, скилл automateskill делает форк и подставляет в `repo:` URL форка (источник можно упомянуть в теле плана).
- `repo-path:` удобнее для длинных задач: локальная копия не пересоздаётся, автоматизация лишь делает `pull --ff-only`.

Правила для тела:
- Пункты формулируй как проверяемые действия («просканируй», «сохрани отчёт в tasks/done/audit.md», «исправь и закоммить»), а не абстракции («улучшить код»).
- Долгие операции (сборки, тесты, запуск кода из репозитория) указывай явно и только если они действительно нужны: исполнитель по умолчанию код не запускает.
- Отчёт отдельного пункта не требует: исполнитель всегда пишет `tasks/done/<имя-плана>.report.md` в целевом репозитории.
- Файл плана нельзя использовать как место для секретов: он коммитится в runner и пушится на GitHub.

## Цепочка фаз (анализ → план исправлений → выполнение)

Фаза 2 оформляется как отдельный план, который исполнитель фазы 1 создаёт сам в ходе выполнения. В теле фазы 1 добавь пункт-предписание, например:

```markdown
4. По результатам анализа составь план исправлений: md-файл с frontmatter
   (repo-path: <тот же целевой репозиторий>, executor: plan-executor-sol) —
   пункты исправления по каждой найденной ошибке. Сохрани его в эту же папку
   (см. «Генерация нового плана» в определении исполнителя), закоммить в runner
   и запушь. В итоговом сообщении назови имя созданного файла.
```

Оркестратор после выполнения фазы 1 пересканирует папку и выполнит сгенерированный план указанным в нём исполнителем. Лимит — 10 планов на запуск автоматизации; следи, чтобы цепочка не была бесконечной (каждый следующий план должен уменьшать объём работы).

## Готовый пример (аудит кода с исправлениями)

```markdown
---
repo: https://github.com/BloodyEagle/my-repo.git
executor: plan-executor
branch: obs/code-audit
---
1. Просканируй код репозитория на ошибки: только чтение, код не запускать.
   Сфокусируйся на <области/языках>.
2. Составь отчёт: файл tasks/done/code-audit.md — таблица ошибок
   (файл, строка, суть, серьёзность).
3. По каждой значимой ошибке сформулируй исправление.
4. Составь план исправлений: md-файл с frontmatter
   (repo-path: <локальная копия этого репозитория>, executor: plan-executor-sol),
   по одному пункту на ошибку, сохрани в эту же папку, закоммить в runner
   и запушь. В итоговом сообщении назови имя файла.
```
