# Hindsight Memory Rules
## Bank

- bank_id: имя репозитория, один банк на проект.
- Never create new banks without asking user.

## Разделение труда с графом (главное правило)
|Вопрос|Инструмент|
|------|----------|
|Где определён символ / селектор|graph (op: symbol / selector)|
|Кто использует файл, что он использует, цепочки, циклы|graph (op: rdeps / deps / path / cycles)|
|Где встречается текст|search|
|Почему так решено, какие альтернативы отвергнуты|recall|
|Конвенции, предпочтения пользователя, его поправки|recall|
|«За что отвечает модуль», домен↔код|recall → точное место через graph/search|

Память — не источник истины о структуре проекта: граф всегда актуален, записи памяти устаревают.Запись, ссылающаяся на файлы или зависимости, — подсказка: перед опорой на неё проверь графом.

## Инициализация банка (однократно)

Если recall по «project profile overview architecture» пуст — проект не описан. Собери компактный профильчерез скилл, НЕ читая проект целиком:

1. graph op:stats — размер, состав по типам, topImported (хабы проекта).
2. package.json, angular.json — стек, версии, ключевые библиотеки.
3. graph op:node для 3–5 хабовых файлов — крупные сущности.
4.  Структура src/app на уровне папок/модулей.

Retain 5–8 записей:

- project-profile — стек, версии, сборка, ключевые библиотеки.
- structure — слои и организация src/app (уровень папок и модулей, не файлов).
- conventions — фактические паттерны и договорённости проекта.
- domain-map — соответствие бизнес-терминов и модулей/сервисов, одна строка на модуль.
- gotchas — неочевидное, ловушки, легаси-оговорки.

Гранулярность — папки, модули, домены. Не файлы, не номера строк, не зависимости:это территория графа, в памяти оно протухает первым.Обновляй профиль только по запросу пользователя или после крупного рефакторинга.

## When to Recall

- В начале нетривиальной задачи в малознакомой части проекта — один recall по теме задачи.
- Вопросы «почему», «как решали», конвенции, предпочтения.
- «Где логика X» по бизнес-термину: recall (домен→код), затем graph/search для точного места.
- Never say "nothing found" without recalling first.

## When to Retain

- Решение с обоснованием, неочевидное из кода (выбранный подход, отвергнутые альтернативы).
- Договорённость или конвенция, подтверждённая пользователем.
- Поправка пользователя — это выученное предпочтение.
- Явные «запомни», «сохрани», «запиши».
- Неочевидная ловушка проекта, которую трудно найти в коде.

Одна тема — одна запись (атомарность): теги распространяются на все факты записи,упаковка разных тем в одну запись портит поиск.

## Чего НЕ retain

- Списки файлов, номера строк, зависимости, содержимое кода — graph и search отвечаютна это точнее и всегда свежо.
- Всё, что меняется за недели разработки: у памяти нет инвалидации.
- Дубли одной информации в разных записях.

## When to Update

- Переименован/удалён модуль или крупная сущность → правка domain-map / structure.
- Ловушка из gotchas устранена → удалить запись.
- Обновление = recall (id) → delete → retain новой версии; решения дополняй, не перезаписывай.
- Не обновляй память «на всякий случай» после обычных правок: если запись ссылается на код — она проверяется графом при чтении.

## Tag conventions

- kebab-case: auth-service, не AuthService.
- Английские теги даже в русском контенте; component-теги отдельно от domain-тегов.
- Служебные: architecture, overview, conventions, domain-map, gotchas, decision.
